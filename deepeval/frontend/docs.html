El flujo completo

Cada suite evalúa a un agente. El ciclo entero, de tocar el prompt a ver el resultado aquí:

  1. Defines los casos en suites/<suite>/cases.py: cada caso es una entrada (lo que recibe tu agente: un mensaje, una pregunta…), el contexto o plantilla que debería usar y un rubric con los criterios de calidad.
  2. Ejecutas script/deepeval/run_deepeval.sh <suite> [--fresh]. Primero se generan las respuestas del agente evaluado (una llamada al modelo por caso) y se cachean en out/responses/<suite>.json — con --fresh se regeneran; sin él, se reutilizan.
  3. DeepEval evalúa cada respuesta con pytest: checks de texto (gratis), la métrica Faithfulness (detector de datos inventados) y dos GEval (reglas globales del prompt + rubric del caso). Un modelo juez puntúa de 0 a 1 cada métrica; se aprueba desde 0,5.
  4. Se archiva el resultado: el JSON del run se copia a out/history/<suite>/run-AAAAMMDD-HHMMSS.json y se reconstruye el índice out/history/index.json.
  5. Este panel lo pinta: sirve la carpeta con script/deepeval/view_deepeval.sh y el frontend lee el índice y todos los runs de la suite. Sin backend: solo ficheros estáticos.

Para iterar el prompt del agente: cambias el prompt → --fresh → comparas el run nuevo contra el anterior en la sección Respuestas del agente (diff palabra a palabra) y miras si las notas subieron o bajaron.

Formato que lee el frontend

El panel es un visor genérico de resultados DeepEval. Para que cualquier eval tuyo aparezca aquí solo necesita dos cosas dentro de out/history/:

1 — El índice de suites

out/history/index.json { "mi_agente": ["run-20260815-193200.json", "run-20260815-211600.json"], "otro_agente": ["run-20260816-100000.json"] }

Un objeto {suite: [ficheros]}. Cada clave se convierte en un botón del selector de suites. El script de run lo reconstruye solo escaneando out/history/*/run-*.json.

2 — Un JSON por run

Es el fichero que DeepEval deja en .deepeval/.latest_test_run.json tras cada ejecución, copiado con nombre run-AAAAMMDD-HHMMSS.json (de ahí sale la fecha que ves en el historial). Estructura mínima que usa el panel:

{ "testRunData": { "testCases": [ { "name": "test_mi_agente[caso-ejemplo]", ← el nombre del caso va entre corchetes "input": "…la entrada del caso…", "actualOutput": "…la respuesta del agente…", "retrievalContext": ["…contexto/plantilla usada…", "…entrada…"], "success": true, "metricsData": [ { "name": "Faithfulness", ← nombre de la métrica "score": 0.94, "threshold": 0.5, "success": true, "reason": "…veredicto razonado del juez…", "verboseLogs": "…análisis paso a paso…", "evaluationModel": "gpt-4.1-mini", "evaluationCost": 0.0015, "inputTokenCount": 1963, "outputTokenCount": 457 } ] } ], "testPassed": 5, "testFailed": 3, "runDuration": 72.1, "evaluationCost": 0.027, "hyperparameters": { "Suite": "mi_agente", "Modelo evaluado": "…", … } } }

Anatomía de una suite

Todo lo específico de un agente vive en su carpeta:

deepeval/ ├── suites/<suite>/ │ ├── prompt.json el prompt real del agente en formato chat (system + user) con huecos {{…}} │ ├── agent.py invoca al modelo EVALUADO igual que en producción (modelo, temperatura, response_format) │ └── cases.py los casos de prueba con sus rubrics y las reglas globales ├── tests/test_<suite>.py un test de pytest por suite (métricas + hyperparameters) ├── core/generate_responses.py genérico: genera y cachea respuestas de cualquier suite └── out/ todo lo generado (caché, historial) — no se versiona

Por qué se manda el prompt entero y no solo la entrada: si le mandas al modelo la entrada "a pelo" no estás evaluando a tu agente, sino a un modelo genérico. prompt.json es una copia del prompt real del agente; si lo cambias en el agente, actualiza también esta copia.

Añadir una suite nueva

  1. Crea suites/<nombre>/ con agent.py, cases.py y prompt.json (copia los de una suite existente y adapta).
  2. Crea tests/test_<nombre>.py (copia el de mail, cambia los imports y la constante SUITE).
  3. Ejecuta script/deepeval/run_deepeval.sh <nombre> — la suite aparece sola en el selector de este panel.

Cómo se escribe un caso

Un caso es un dict en la lista CASES de suites/<suite>/cases.py:

{ # Identificador: nombra el test y la entrada en la caché de respuestas "id": "caso-ejemplo", "description": "Descripción corta del escenario", # 1. El contexto/plantilla que el agente debería usar (fichero real de tu agente) "skill_file": SKILLS_DIR / "plantilla-ejemplo.md", # 2. La entrada del caso: lo que recibe tu agente "message": ( "De: cliente@ejemplo.com\n" "Asunto: Consulta de ejemplo\n\n" "Hola, tengo una duda sobre el estado de mi solicitud. ¿Me podéis informar?" ), # 3a. Checks deterministas: baratos y exactos (ignoran mayúsculas) "contains_any": ["solicitud", "consulta"], # al menos uno debe aparecer # "contains_all": [...], # todos deben aparecer # 3b. Rubric del caso: criterios en lenguaje natural que valida el juez "rubric": ( "1. Saluda al remitente.\n" "2. Resume lo que pide (información sobre su solicitud).\n" "3. NO afirma datos que la entrada no contiene ni promete plazos inventados.\n" "Suspende si incumple cualquiera." ), # "expect_fail": True, # solo para canarios: marca el test como xfail(strict) }

A cada caso se le aplican automáticamente cuatro capas, de la más barata a la más cara:

  • Checks de texto — sin LLM: términos obligatorios y sin \n literal en la respuesta.
  • Faithfulness — descompone la respuesta en afirmaciones y contrasta cada una contra el contexto (entrada + plantilla). Es el detector de alucinaciones.
  • GEval reglas-globales — el juez valida las reglas transversales de tu prompt (p. ej. idioma, tono, estructura, formato de salida, qué está prohibido decir).
  • GEval rubric-<caso> — el juez valida el rubric específico del escenario.

Después de añadir un caso, ejecuta con --fresh para que se genere su respuesta.

Configuración y modelos

En cada eval intervienen dos modelos con papeles distintos:

RolDónde se configuraQué hace
Evaluadosuites/<suite>/agent.py (EVALUATED_MODEL, TEMPERATURE, MAX_COMPLETION_TOKENS)Hace de agente: recibe la entrada y redacta la respuesta. Es a quien se examina.
Jueztests/test_<suite>.py (JUDGE_MODEL)Puntúa Faithfulness y los GEval leyendo la respuesta del evaluado. Los checks de texto no usan ningún modelo.

Se usa un juez pequeño, distinto y estable a propósito: calificar contra criterios es más fácil que redactar, es mucho más barato (~0,02–0,03 $ por run), un modelo no debe calificarse a sí mismo, y al cambiar el evaluado el corrector sigue siendo el mismo — así los runs son comparables.

Claves de API

Van en el .env de la raíz del repo como API_KEY_OPENAI. El conftest.py la expone como OPENAI_API_KEY, que es la variable que DeepEval espera para el juez.

Hyperparameters: cada run se autodocumenta

El test registra en cada run su configuración completa — suite, modelo evaluado, juez, temperatura, max tokens, umbral y la plantilla del prompt usada. Por eso la sección "Configuración del run" puede decirte con qué se generó cualquier run del historial aunque luego hayas cambiado el prompt, y por eso el panel puede marcar "prompt cambiado" automáticamente.

Comandos

script/deepeval/run_deepeval.sh # corre la suite por defecto script/deepeval/run_deepeval.sh <suite> # corre otra suite script/deepeval/run_deepeval.sh <suite> --fresh # regenera las respuestas del agente antes de evaluar script/deepeval/view_deepeval.sh [puerto] # sirve este panel (por defecto http://localhost:8377/frontend/) script/deepeval/clean_deepeval.sh # borra TODO lo generado (caché, historial, cachés de pytest)

A mano, siempre desde dentro de deepeval/ (la carpeta se llama igual que el paquete Python: desde la raíz del repo, import deepeval cargaría la carpeta en vez de la librería):

cd deepeval ../.venv/bin/python -m core.generate_responses <suite> # generar respuestas (opcional) ../.venv/bin/deepeval test run tests/test_<suite>.py # evaluar (genera la caché si falta)

Cuándo usar --fresh: siempre que cambies el prompt del agente o sus plantillas. Sin él estarías evaluando respuestas viejas de la caché. Ojo: clean_deepeval.sh borra también el historial de este panel.

Los canarios: tests que deben fallar

Un canario es un caso cuyo rubric exige algo que el prompt del agente prohíbe. Si el agente se comporta bien, el rubric suspende → el caso sale ✗ mal, y eso es lo correcto. Cada canario vigila una regla distinta del prompt. Ejemplos del patrón:

  • Un rubric que exige cifras o datos concretos que la entrada no trae — si "pasa", el agente está inventando datos.
  • Un rubric que exige algo que el prompt prohíbe decir (p. ej. remitir el caso a un tercero) — si "pasa", el agente está rompiendo esa regla.
  • Un rubric que exige romper el formato de salida (metacomentarios, campos extra) — si "pasa", el agente está ensuciando la salida.

En pytest van marcados xfail(strict=True): la suite queda en verde (N passed, M xfailed) y, si algún día un canario "aprueba", pytest lo eleva a error XPASS — la alarma de que el agente ha empezado a hacer algo prohibido. No los "arregles".

Trucos del panel

  • Leyenda clicable: clic en una serie del gráfico para ocultarla/mostrarla.
  • Por métrica / Por caso: medias por familia de métrica, o la evolución de cada caso individual (útil para ver qué escenario concreto empeora al tocar el prompt).
  • Comparar respuestas: en "Respuestas del agente", elige otro run y verás el diff palabra a palabra (tachado = antes, resaltado = ahora) y cuántas respuestas cambiaron.
  • Buscador y "solo fallos": filtran la tabla de casos y las respuestas; busca también dentro de los veredictos del juez.
  • Detalle de un caso: clic en su fila → email, respuesta, plantilla cargada y, por métrica, el veredicto del juez, su análisis paso a paso (las afirmaciones que extrajo y cuáles tienen respaldo) y los tokens/coste.
  • Exportar CSV: descarga los datos de la vista actual del gráfico.
  • URL compartible: ?suite=<suite>&mode=casos&view=tabla&compare=0 abre el panel en ese estado exacto.
